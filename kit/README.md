# brick kit

A component library for brick: buttons, forms, overlays, data tables, charts and app layouts, rendered on the server. Every component works without JavaScript and gets better with it. The showcase site in `examples/ui` has a page for every component and demo apps built only from the kit (`task ui:serve`, then http://localhost:8002).

## Using it

The kit is a component library: a folder with a `brick-library.yaml` manifest. List it once and every kit tag is available by name on every page, with no `use:` and nothing to copy. There are three ways to get it:

- **With the brick CLI**, which ships the kit, name it in `brick.yaml`:

  ```yaml
  libraries: [brick-kit]
  ```

- **From Go**, the kit is embedded in the `github.com/ubgo/brick/kit` package:

  ```go
  opts := brick.Options{FS: root.FS(), Libraries: []brick.Library{kit.Library()}}
  ```

  To let `brick.yaml` name it instead, offer it to the config: `cfg.Apply(&opts, kit.Library())`.

- **Remotely**, from the repository at a version, then run `brick vendor`:

  ```yaml
  libraries:
    - github.com/ubgo/brick/kit@main
  ```

Your own components always win a name over the kit's, and a clash is logged. To take only some components, or to keep two libraries' `Button`s apart, use `only:` and `prefix:` (`{from: brick-kit, prefix: Bk, only: [Button, Dialog]}` gives `<BkButton>`). A single component can still be imported on its own with `use: Dialog: github.com/ubgo/brick/kit/components/Dialog.html@main`.

The layout needs only the assets line:

```html
<body class="bk-base">
{{ assets }}
…
</body>
```

- `{{ assets }}` goes first in `<body>`, so each component's CSS loads before the content that uses it. The design tokens come with it: the manifest lists `Theme` under `global:`, so its stylesheet is linked on every page that uses the kit. A `<Theme />` line in an older layout still works and is not sent twice.
- `class="bk-base"` on `<body>` is optional. It opts the page in to the kit's base font, colours and focus rings.
- Dark mode follows the system. `data-theme="dark"` or `data-theme="light"` on `<html>` forces one, and `<ThemeToggle />` switches it. `data-accent="emerald"` changes the primary colour; the choices are indigo (the default), blue, emerald, rose, amber, violet and zinc.

Retheme by overriding the `--bk-*` custom properties in your own stylesheet. The token list is in `kit/components/Theme.html`.

## Authoring rules

`kit_lint_test.go` enforces the rules marked ✱ on every file in `kit/components`.

1. **One file, one component.** Name it in PascalCase. Its root element carries the class `bk-<name>` (kebab-case), with modifiers `bk-<name>--<modifier>` and parts `bk-<name>__<part>`.
2. ✱ **A doc comment first.** Open the file with a `{{/* … */}}` comment. It says what the component is, gives two to five example calls, and states any invariant a caller must respect.
3. **Declare every prop** with a type and a default. Closed sets use `oneof:`, so a typo is an error rather than an unstyled box. Common names:
   - `variant`
   - `size`: `xs`, `sm`, `md` or `lg`, default `md`
   - `icon`
   - `label`: the accessible name
   - `disabled`
4. ✱ **Pass the caller's attributes through.** Merge the caller's class with `class="{{ cx `bk-x` … .Attrs.class }}"`. Write the rest with `{{ attrs `class` }}`, so the root never gets two class attributes. `id`, `aria-*`, `data-*` and `hx-*` must reach the root.
5. ✱ **Global CSS, prefixed.** Write styles in a plain `<brick:style>` (never `scoped`), where every selector sits under a `.bk-` class. A class then works on any element, the kit works on browsers without `@scope`, and host markup is never touched.
6. ✱ **Tokens only.** Use `var(--bk-*)` for colours. For tints, use `color-mix(in oklab, var(--bk-primary) 12%, transparent)`. Literal hex, `rgb()` and `hsl()` values belong only in `Theme.html`.
7. **Compact and consistent.**
   - Control heights come from `--bk-h-*`. `md` is 2rem, the default.
   - Text uses `--bk-text-sm` (13px) for controls and `--bk-text-base` (14px) for body.
   - Radii come from `--bk-radius*`, and transitions last `var(--bk-duration)`.
8. **Progressive.** The HTML must be complete and usable with JavaScript off:
   - A dialog is a native `<dialog>`; its trigger falls back to a link or `popovertarget`.
   - A dropdown is a `<details>`.
   - Tabs show every panel.
   
   A `<brick:client>` module enhances that HTML through `brick.mount("Name", (el, props) => { …; return cleanup })`. The module never builds the markup itself.
9. **Accessible.**
   - Use the native element first.
   - Otherwise follow the WAI-ARIA pattern: roles, `aria-expanded`, `aria-controls`, a roving tabindex, and Escape to close.
   - Every icon-only control takes a `label`.
10. ✱ **Import other kit components by path, from the library root:** `use: Icon: ~/components/Icon.html`, and data as `~/data/icons.yaml`. Inside a library `~/` means the folder holding `brick-library.yaml`, so the same path works embedded, vendored or copied. Never reach outside `~/components/` and `~/data/`.
11. ✱ **Icons come from `kit/data/icons.yaml`**, adapted from Lucide (ISC). Add a missing one there. The test fails on an unknown literal name.
12. **Server state through actions.** A component that changes data declares `state:` and Starlark actions (see the guide's *Actions* section). Code that is not a click, such as drag and drop, calls `brick.action(el, "name", args)`.
13. **Tested.**
    - Every component has a page in `examples/ui/content/components/`, and every example on it is a component file in `examples/ui/demos/`.
    - The showcase tests assert the rendered HTML.
    - Components with a client module have a jsdom test in `kit/test/`.
